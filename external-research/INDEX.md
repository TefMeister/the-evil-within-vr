| 2026-09-07 | [Deferred `Map` hands back command-list scratch memory — so a per-eye edit is baked into the list](topics/2026-09-07-deferred-map-hands-back-scratch-memory-so-a-per-eye-edit-is-baked-into-the-command-list.md) | 🆕 new | ⚠️ **Read the "already known" section first** — the commissioned research's headline recommendations are **already implemented here**: `(ctx,res)` keying (the re-test's own table says so), draw-time buffer substitution (the pool path), and the deferred-context count (**six**, measured here; the public record has **nothing** on id Tech 5 / STEM's D3D11 threading, and that gap is assessed as genuine — id's own id Tech 5 shipped **OpenGL**, and this game's D3D11 backend is Tango's own addition with no public technical writing). ⭐ **What survives (1): `unmaps==0` has a second cause.** The reading table attributes it to the vtable flavour; there is also a **semantic** cause `[reported 2026-09-07]` — on a deferred context `Map` does not touch the real resource but returns a **fresh scratch allocation owned by that context's command list**, committed on replay. In DXVK's implementation of the contract, **`Unmap` on a deferred context is a no-op, the update being committed *in* `Map`** (`WRITE_DISCARD` allocates a new slice; `WRITE_NO_OVERWRITE` errors without a prior discard on that list). So a zero count need not mean the hook is blind — separate the two by counting whether `Unmap` is reached on *any* context. It also supplies the **reason** the current key is correct: the same constant buffer can legitimately be mapped on **two deferred contexts simultaneously**, so resource-alone is unsafe. And the cleanest statement of why the original per-thread ring was on the wrong axis, from first-party vendor documentation (*"only one thread can call a ID3D11DeviceContext at a time"*): **threads are unbounded and transient; contexts are few and stable** — which also means a per-context table needs **no inner lock at all**. ⚠️ **(2) A named deadlock this hook shape is prone to** — 3Dmigoto issue #104, *"Lock ordering bug (Deadlock) between 3DMigoto and DirectX"*: take your critical section → call into D3D → D3D takes its lock → calls `Release()` → re-enters your release tracker → tries to retake your section. **Never hold a global lock across a call back into D3D inside a `Map`/`Unmap` hook.** With six deferred contexts and a shared table this project has that exact shape; a deadlock presents as a hang and costs a launch. One read before the re-test. ⚠️⚠️ **(3) A structural limit on Map-time stereo, deliberately parked and not filed as an action.** A value written at `Map` time on a deferred context is **baked into the recorded command list**, so it cannot express a different value for the two eyes from a single recorded upload `[hypothesis]` — a consequence of the documented model, not observed here. **Irrelevant to the pending mono re-test** (`TEST_YAW=90`), and the pool path already works at draw time where it does not apply; revisit only if the mono re-test passes and stereo is next. Corroborating the direction: **3Dmigoto's canonical stereo mechanism is not CPU-side constant-buffer editing at all** — it injects a stereo-parameter resource and patches the shaders, using Map interception mainly for hashing and contamination tracking. Also noted: RenderDoc keys its open-map table on resource **and subresource** while 3Dmigoto keys on resource alone and **silently no-ops an unpaired `Unmap`** — for constant buffers the subresource is always 0, so a nicety here, but the no-op precedent matters since this project counts unpaired unmaps. ⚠️ Two forum threads 403'd, so a couple of corroborating quotes are second-hand snippets and are marked as such; the load-bearing claims are vendor documentation and source. |
